## Decision

Keep the current three-part deployment:

```text
Browser ──> Vercel: apps/web (Next.js)
   │              │ Next route handlers for web-only features
   │              └──> HTTPS API URL
   ├──> Supabase Auth
   └──> HTTPS API: apps/api (Spring Boot, one always-on VM)
                    ├──> Supabase Postgres and Storage
                    └──> Gemini
```

`apps/web` already calls the versioned API through `NEXT_PUBLIC_API_BASE_URL`; `apps/api` verifies Supabase JWTs and applies CORS from `WEB_ALLOWED_ORIGINS`. The web app also has a few Next route handlers, so “separate frontend and API” means separate deployable services, not that Vercel runs zero server code. `packages/shared` supplies shared TypeScript types. Do not move the JVM API into Vercel Functions or change the repository layout for this launch.

**Public launch preference:** Vercel Pro + the existing Supabase project on Pro + a single 2 GB AWS Lightsail VM near that project's region. This is approximately **$57/month fixed platform cost** before AI, domain, email overages, taxes, and traffic overages: $20 Vercel + $25 Supabase + $12 Lightsail. These are list prices, not a quote for this account or region. [Vercel Pro](https://vercel.com/docs/plans/pro-plan), [Supabase pricing](https://supabase.com/pricing), [Lightsail pricing](https://aws.amazon.com/lightsail/pricing/).

**Lower-cost beta option:** Try an Oracle Always Free A1 VM first, with a 30-minute provisioning limit. If available in the account's home region and close to the existing Supabase project, it removes the $12 VM fee. Oracle currently documents an allowance equivalent to 2 OCPUs and 12 GB RAM; it also documents capacity failures and possible reclamation of idle free instances. This is a beta cost optimization, not an availability guarantee. If the home region is far from Supabase or capacity is unavailable, use Lightsail. [Oracle Always Free terms](https://docs.oracle.com/en-us/iaas/Content/FreeTier/freetier_topic-Always_Free_Resources.htm).

Vercel Hobby ($0) is for personal, non-commercial use and cannot connect a Hobby project to a GitHub organization-owned repository. Treat Pro as the budget for a public product on the current organization repository; do not plan the launch around Hobby eligibility. [Vercel terms](https://vercel.com/legal/terms), [Vercel Git repository limit](https://vercel.com/docs/limits). Supabase Free is suitable only for a small private beta: it has no automatic backups, 1 GB file storage, 5 GB egress, a 500 MB database quota, and can pause after a week of inactivity. [Supabase pricing](https://supabase.com/pricing), [production checklist](https://supabase.com/docs/guides/deployment/going-into-prod).

The GCP always-free `e2-micro` VM is available only in specified US regions and has 1 GB RAM, so it is a poor fit for this India-focused JVM API beside a Mumbai database. Cloud Run's scale-to-zero/request-based mode does not give this code reliable CPU for its scheduled lease, deletion, and retention jobs; keeping a minimum instance with background CPU incurs cost and adds a configuration change. New AWS free credits are temporary, not a permanent $0 server plan. [GCP free tier](https://docs.cloud.google.com/free/docs/free-cloud-features), [Cloud Run billing](https://docs.cloud.google.com/run/docs/configuring/billing-settings), [AWS Free Tier](https://aws.amazon.com/free/free-tier-faqs/).

## Launch sequence

1. **Confirm the exact release commit and database state.** Check the web, API, database, and image CI jobs on the exact `develop` SHA. Run `npm run supabase -- migration list --linked` and resolve every migration missing remotely before deploying code that reads it; if a migration must be applied, follow the repository's `npm run db:push` gate. A green local build does not replace green CI. Keep `main` untouched: only the owner advances it through a release PR.
2. **Prepare the existing Supabase project.** Confirm its actual region before choosing the VM region. For public use, upgrade to Pro, configure custom SMTP and test a non-team signup address, set the production Site URL and `/auth/callback` redirect allow-list, and check Google OAuth redirect settings. Supabase's built-in mailer is restricted and intended for non-production use. Complete a database restore drill before accepting user data. [Supabase SMTP](https://supabase.com/docs/guides/auth/auth-smtp).
3. **Deploy the API on one VM.** Build the existing `apps/api/Dockerfile`; run it with a restart policy and a memory limit appropriate to the chosen VM. Put Caddy or an equivalent reverse proxy in front for HTTPS. Expose ports 80/443 publicly, not the Spring port or database. Configure server-only `DATABASE_URL`, `DATABASE_USER`, `DATABASE_PASSWORD`, `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, `GEMINI_API_KEY`, `WEB_ALLOWED_ORIGINS`, and AI limits outside Git. Use the Supabase session pooler on port 5432, as `.env.example` specifies. Check `/actuator/health/readiness`, logs, and a non-AI authenticated endpoint. Do not infer that a 2 GB VM has adequate headroom until its memory is observed under real use.
4. **Deploy the web app as one Vercel monorepo project.** Root Directory: `apps/web`; include files outside that directory for `packages/shared` if Vercel does not include them automatically. Production branch: `develop`. Set `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`, and `NEXT_PUBLIC_API_BASE_URL=https://<api-host>` before the production build; public variables are compiled into the web bundle. Put Vercel Functions near the actual Supabase region (`bom1` only when Mumbai is appropriate). Static assets remain on Vercel's CDN. Add only the production web origin to `WEB_ALLOWED_ORIGINS`; preview URLs need a separate decision. [Vercel monorepos](https://vercel.com/docs/monorepos), [Function regions](https://vercel.com/docs/functions/configuring-functions/region).
5. **Set launch controls.** Set `AI_DAILY_SPEND_CAP_MICRO_USD` to a nonzero pilot threshold and review `AI_PER_USER_DAILY_CAP_MICRO_USD`. Also set a Gemini project monthly spend cap in AI Studio or an eligible Cloud Billing spend-cap budget. The in-app daily guard only stops *optional* AI calls after its threshold; it preserves an in-progress interview and report. It is not a hard bill ceiling. If `FALLBACK_PROVIDER_API_KEY` is set, cap that provider separately; leaving the optional key unset avoids a second bill during the first pilot. Monitor fallback rate, AI ledger, VM health, and Supabase usage. Configure Turnstile in both the web app and Supabase Auth before opening email signup to the public. [Gemini billing](https://ai.google.dev/gemini-api/docs/billing/), [Cloud spend caps](https://docs.cloud.google.com/billing/docs/how-to/budgets-spend-caps).
6. **Check and release.** Verify HTTPS, landing page, OAuth and email signup callbacks, authenticated dashboard, resume upload and deletion, and API readiness. Check that the legal operator and grievance details no longer show their placeholder values. A full spoken round and its report require the owner's explicit go-ahead for live AI spend and human review of voice quality and latency. Start with a small invited group and read the actual cost per round before broad promotion.

If the CI, linked migrations, SMTP, backup restore, or auth checks cannot be completed today, publish only a landing-page preview: disable the product feature flags in both deployments, disable new signups in Supabase, and check the remaining `/login` path and CTA copy. The landing page tolerates a missing public usage counter, but it still needs valid public Supabase build variables; verify the resulting page in a browser. This is a staged release, not a claim that the interview product is live.
